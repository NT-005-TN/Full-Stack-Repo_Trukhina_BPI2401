# Система опросов и голосований

Учебное full-stack приложение для создания и прохождения опросов. Проект разрабатывается последовательно в рамках лабораторных работ курса Fullstack.

## Назначение

Приложение позволяет зарегистрированным пользователям создавать опросы с несколькими вопросами, участвовать в чужих опросах и просматривать опубликованные результаты. Для публичных опросов доступно гостевое участие без регистрации.

## Обязательный стек

- Backend: Python и FastAPI.
- База данных: PostgreSQL.
- ORM: SQLAlchemy.
- Frontend: React и TypeScript.
- Контроль версий: Git.

В лабораторной работе №1 разрабатывается frontend с демонстрационными данными без подключения backend и базы данных.

## Лабораторная работа №1

Frontend реализован на демонстрационных данных. В проекте используются:

- React и TypeScript;
- Material UI;
- React Router;
- Vite;
- локальное состояние React и `sessionStorage`.

Реализованы поиск и просмотр опросов, гостевой режим, демонстрационные вход и регистрация, разграничение доступа, создание опроса с несколькими вопросами, история, управление статусами, прохождение, проверка и отправка ответов, а также агрегированные анонимные результаты.

Демонстрационная авторизация и данные существуют только во frontend. Настоящие пользователи, ответы и опросы будут храниться через backend и PostgreSQL в следующих лабораторных работах.

## Пользователи

### Гость

Гость может открыть публичный опрос по ссылке, ответить на вопросы и посмотреть опубликованные результаты. Гость не может создавать опросы и не имеет постоянной истории.

### Зарегистрированный пользователь

Зарегистрированный пользователь может проходить опросы, создавать собственные опросы и просматривать историю. Один пользователь может одновременно выступать голосующим и создателем.

## Основные пользовательские сценарии

### Прохождение опроса

1. Пользователь открывает список доступных опросов.
2. Выбирает активный опрос.
3. Последовательно отвечает на несколько вопросов.
4. Переходит между вопросами с помощью кнопок «Назад» и «Далее».
5. Проверяет выбранные ответы.
6. Подтверждает отправку.
7. Получает сообщение об успешном завершении.

### Создание опроса

1. Зарегистрированный пользователь открывает форму создания.
2. Вводит название и описание.
3. Добавляет несколько вопросов и варианты ответов.
4. Выбирает режим доступа: только для зарегистрированных пользователей или для всех по ссылке.
5. Настраивает срок проведения и публикацию результатов.
6. Сохраняет черновик или публикует опрос.

### Просмотр истории

1. Пользователь открывает страницу «История».
2. Во вкладке «Мои участия» видит пройденные опросы.
3. Во вкладке «Созданные» видит собственные опросы и их статусы.
4. Если результаты опубликованы, пользователь может открыть их.

## Анонимность

Система должна хранить факт участия отдельно от выбранных ответов. Создатель видит только общую статистику и не может определить, какой вариант выбрал конкретный пользователь. В истории отображается факт прохождения, но не индивидуальные ответы.

## Основные экраны

- вход и регистрация;
- список опросов;
- информация об опросе;
- прохождение опроса с несколькими вопросами;
- проверка ответов;
- успешное завершение;
- результаты;
- история участий и созданных опросов;
- создание и редактирование опроса;
- управление опросом;
- страница 404.

## Лабораторная работа №2

Backend находится в каталоге `backend` и использует FastAPI, PostgreSQL и SQLAlchemy.
Параметры подключения к базе данных читаются из окружения; пример без секретов
сохранён в `backend/.env.example`.

Первоначальная настройка backend:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
python -m app.init_db
uvicorn app.main:app --reload
```

Перед командой `python -m app.init_db` создайте пустую локальную базу PostgreSQL
с именем `polls` и укажите строку подключения в `backend/.env`. Команда создаст
восемь связанных таблиц из моделей SQLAlchemy. Файл `.env` исключён из Git;
репозиторий содержит только безопасный пример `.env.example`.

После запуска проверка состояния API доступна по адресу
`http://localhost:8000/health`, а интерактивная документация — по адресу
`http://localhost:8000/docs`.

Запуск тестов:

```bash
cd backend
source .venv/bin/activate
pytest
```

### Модель данных

- `users` — зарегистрированные пользователи;
- `polls` — опросы и их настройки, каждый опрос принадлежит пользователю;
- `questions` — вопросы опроса;
- `options` — варианты ответа на вопрос;
- `participations` — отдельный факт участия пользователя в опросе;
- `submissions` — анонимная отправка набора ответов;
- `answers` — выбранный вариант для каждого вопроса отправки.
- `refresh_tokens` — хеши refresh-токенов, сроки действия и признаки отзыва.

Вопросы связаны с опросом, варианты — с вопросом, а ответы — с анонимной
отправкой. У `submissions` намеренно нет ссылки на пользователя: создатель
опроса может получить общую статистику, но не может сопоставить ответы с
конкретным участником. Факт участия хранится отдельно в `participations`.

### API опросов

- `GET /polls` — получить список опросов;
- `GET /polls/{poll_id}` — получить опрос с вопросами и вариантами;
- `POST /polls` — создать опрос с вопросами и вариантами;
- `PATCH /polls/{poll_id}` — изменить основные настройки опроса;
- `DELETE /polls/{poll_id}` — удалить опрос и связанные записи.

API проверяет обязательные поля, допустимые статусы и настройки, наличие хотя
бы одного вопроса и двух вариантов, будущую дату окончания и существование
владельца. Некорректные данные возвращают статус `422`, отсутствующие записи —
`404`.

### API пользователей

- `GET /users` — получить список пользователей;
- `GET /users/{user_id}` — получить пользователя;
- `POST /users` — зарегистрировать пользователя;
- `PATCH /users/{user_id}` — изменить почту или пароль;
- `DELETE /users/{user_id}` — удалить пользователя без созданных опросов.

Почта валидируется и должна быть уникальной. Пароль должен содержать не менее
восьми символов, сохраняется только его PBKDF2-хеш с уникальной солью и никогда
не возвращается API.

### Голосование и результаты

- `POST /polls/{poll_id}/submissions` — отправить ответы на все вопросы;
- `GET /polls/{poll_id}/results` — получить агрегированное число голосов.

API принимает ответы только для активного и не завершившегося по дате опроса,
проверяет каждый вопрос и принадлежность выбранного варианта. Для закрытого
опроса требуется пользователь, повторное участие зарегистрированного
пользователя отклоняется. Факт участия записывается отдельно от анонимной
отправки ответов, а API результатов не возвращает пользовательские данные.

## Основные маршруты

- `/` — список и поиск опросов;
- `/login` — вход, регистрация и гостевой режим;
- `/polls/:pollId` — информация перед началом;
- `/polls/:pollId/vote` — прохождение опроса;
- `/polls/:pollId/results` — опубликованные результаты;
- `/create` — создание опроса после входа;
- `/history` — история участий и созданных опросов;
- `/manage/:pollId` — управление созданным опросом.

## Лабораторная работа №4

Frontend и backend используют настоящую авторизацию. Регистрация и вход выполняются
через FastAPI, после чего клиент хранит токены только до закрытия вкладки. При загрузке
приложение проверяет текущую сессию, а при истечении access token один раз обновляет
его с помощью refresh token.

Пароли сохраняются только как PBKDF2-хеши с индивидуальной случайной солью. Access
token является JWT с подписью HMAC-SHA256 и коротким сроком действия. Refresh token
представляет собой криптографически случайную строку; в таблице `refresh_tokens`
хранится только её SHA-256-хеш, срок действия и признак отзыва. При обновлении старая
строка отзывается и выдаётся новая. При выходе refresh token текущей сессии также
отзывается.

Маршруты авторизации:

- `POST /auth/register` — регистрация и выдача пары токенов;
- `POST /auth/login` — вход и выдача пары токенов;
- `POST /auth/refresh` — обновление и ротация токенов;
- `POST /auth/logout` — отзыв refresh token;
- `GET /auth/me` — получение текущего пользователя по access token.

Создание, изменение и удаление опросов защищены. Владелец определяется по JWT,
поэтому клиент не может выполнить операцию от имени другого пользователя. Профиль
также доступен для изменения только его владельцу. Публичные опросы разрешено
проходить гостю, а для закрытых опросов требуется действующий access token.

Для локального запуска задайте собственный `JWT_SECRET` в `backend/.env`. Значения
сроков действия можно изменить через `ACCESS_TOKEN_MINUTES` и `REFRESH_TOKEN_DAYS`.

## Лабораторная работа №5

Основные страницы frontend подключены к FastAPI. Демонстрационные массивы больше
не используются: список, отдельный опрос, история, результаты и управление получают
актуальные данные из базы через общий API-клиент.

Реализованные сквозные сценарии:

- регистрация и вход с последующей проверкой текущего пользователя;
- загрузка доступных активных опросов и просмотр вопросов;
- создание черновика или публикация опроса с несколькими вопросами;
- отправка реальных ответов и отображение агрегированных результатов;
- история участий и список созданных текущим пользователем опросов;
- изменение названия и статуса собственного опроса, а также его удаление;
- автоматическое обновление access token и выход с отзывом refresh token.

Общий клиент показывает ошибки API пользователю и повторяет защищённый запрос после
успешного обновления токенов. На страницах предусмотрены состояния загрузки, ошибки
и отсутствия данных. Backend не принимает переданный клиентом идентификатор владельца:
для создания и изменения используется пользователь из подписанного JWT.

По умолчанию frontend обращается к `http://localhost:8000`. Другой адрес можно
указать в `frontend/.env` через `VITE_API_URL`; безопасный пример находится в
`frontend/.env.example`. Backend разрешает локальный frontend, запущенный как через
`localhost`, так и через `127.0.0.1`.

## Лабораторная работа №3

Frontend разделён по назначению модулей:

- `src/app` — настройка приложения, маршруты и общие стили;
- `src/pages` — страницы приложения;
- `src/entities/poll` — типы и демонстрационные данные опросов;
- `src/shared/ui` — общие компоненты интерфейса.

Структура основана на упрощённых принципах Feature-Sliced Design без лишних
слоёв. Страницы используют общую модель опроса и переиспользуемые компоненты,
поэтому одинаковая разметка и типы не дублируются.

Список опросов демонстрирует состояния загрузки, ошибки и пустого результата.
Ошибка доступна по адресу `/?error=1`, после нажатия «Повторить» данные
загружаются. Для наглядной проверки загрузки можно открыть `/?delay=2000`, а
пустое состояние появляется при поиске отсутствующего названия. Переход между
страницами и появление карточек сопровождаются короткой анимацией; при системной
настройке уменьшения движения она отключается.

Скриншоты `15–17` добавлены после реализации динамических состояний ЛР №3 и
показывают их мобильное отображение.
